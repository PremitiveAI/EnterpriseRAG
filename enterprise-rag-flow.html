File upload

Nothing is trusted. A file passes four independent gates before a row is written, and the hash is taken before anything is stored — so a duplicate never reaches the queue.

Why the hash comes first. Duplicate detection is exact-hash at upload time, so an identical re-upload is answered immediately as DUPLICATE instead of spending an OCR and embedding pass to discover the same thing.
  • MAX20 files per batch, rate limited at 20 uploads/min
  • OUTEach file returns QUEUED, DUPLICATE or REJECTED — one batch, three outcomes
  • DBdocuments row + document_processing row
  • NEXTA Celery task id is handed back so the UI can poll status
2

Document processing

The worker is a separate long-lived process. It walks a fixed state machine, and every stage it enters is written to the database first — so a crash is visible as a stage, not as silence.

OCR is conditional. Text extraction runs first; OCR only engages when a page yields fewer than 50 characters, which is how a scanned PDF is told apart from a born-digital one without asking the user.
Retries are safe. Point ids are derived from uuid5(document_id : chunk_index), so a re-run upserts over its own previous output instead of duplicating it.
3

Chunking

Text is cut into overlapping windows. The overlap is the point: a sentence that straddles a boundary still appears whole in one of the two neighbours.

  • SIZE1000 characters per chunk
  • OVER150 characters of overlap
  • KEEPpage number, section and chunk_index travel with the text
  • WHYA citation has to point back at a page — so position is preserved, not discarded
Without overlap a fact split across a boundary is retrievable from neither half: each fragment on its own is too weak a match to clear the score floor.
4

Embedding generation

Every chunk becomes 768 numbers. This runs locally — no API call, no key, no per-document cost — which is a deliberate architectural decision, not an optimisation.

chunk text
“All permanent employees are entitled to twenty-four days of paid annual leave…”
↓
768-dimensional vector
  • MODELall-mpnet-base-v2, sentence-transformers
  • DIM768, cosine distance
  • WHEREIn the worker process, on CPU
The consequence people miss. Because retrieval never touches the LLM provider, switching the answering model — Gemini to OpenAI, say — does not invalidate a single vector and needs no re-indexing. The two halves of the system are genuinely independent.
5

Vector storage

Vectors land in Qdrant — in one collection per organization. Tenant isolation is structural here: a forgotten filter cannot leak across tenants, because the other tenant's data is not in the collection being searched.

stored chunk vector match query vector
  • COLLorg_<uuid without hyphens>
  • POINTuuid5(document_id : chunk_index) — deterministic
  • LOADtext, document name, page, category, language, tags, status
  • FLAGis_public — what separates the public chatbot's corpus from the admin's
Two ids on purpose. organization_id is carried in the payload even though the collection already implies it — so an audit can prove a stray point did not arrive from another tenant.
6

User query

A question arrives on the synchronous request path. Before anything is searched, agent 2 rewrites it into a standalone search query and may propose metadata filters.

asked
“How many days of annual leave do employees get?”
rewritten by the query planner
…
  • CTXLast 6 turns of conversation, from Redis
  • FILTProposed filters are verified against the corpus and dropped if unverifiable
  • FAILIf the agent fails, retrieval uses the raw question — a failed agent never fails a chat
Why filters get dropped. A filter the corpus cannot satisfy turns a findable answer into an empty result, and an empty result is indistinguishable from “the documents don't say”. So an unverifiable filter is discarded rather than applied.
7

Vector search

The rewritten question is embedded by the same local model, then scored against the tenant's collection. Anything below the floor is not “a weak answer” — it is discarded.

  • TOP-K5 passages (public chatbot: 3)
  • FLOORscore ≥ 0.35
  • SCOPEOne collection — the caller's organization, from the token
The floor is what makes refusal possible. With no threshold the nearest chunk always wins, however irrelevant, and the system would answer every question confidently — including the ones the documents cannot answer.
8

Context + LLM

The prompt is assembled by code, not by the model. Agent 3 receives the passages, the grounding rules and a JSON contract — and only the middle part is editable.

🔒 locked — appended by code, always
Use ONLY the passages above · Do not invent facts · Cite only ids from the list · Return JSON only
  • MODELResolved from the database per call — switchable with no restart
  • OUT{answer, is_grounded, cited_chunk_ids}
  • CHECKCited ids are intersected with the ids actually supplied
Invented citations are dropped. If the model returns ids that were never given to it, they are removed — and if nothing verifiable remains, the system falls back to a templated answer built from the same passages. That is why an answer can suddenly read as a list of excerpts: the model stopped following the contract.
9

Answer + sources

The answer is masked for display, persisted, and returned with the sources it actually cited — or refused, which is a first-class outcome rather than an error.

Refusal is a 200, not an error. When nothing clears the floor the reply is “I could not find this information in the available documents” with NO_RELEVANT_CONTEXT — a correct answer about the corpus, recorded as is_grounded = false.
  • PIIPAN and Aadhaar numbers are masked before display — only values that validate, so an invoice number is left intact
  • SAVEMessage, latency, grounding flag and citations are persisted
  • FLAGdegraded: true when any stage fell back — the answer is real, the path was reduced

What runs where

Two processes, and the split explains most of the design.

  • APIUpload validation, chat, retrieval, agents 2 & 3 — synchronous, latency matters
  • WORKERExtraction, OCR, enrichment, agent 1, chunking, embedding, indexing — async, nobody waiting
  • SHAREDPostgreSQL is the source of truth. Redis is a broker and a cache, never truth
They never coordinate directly. Both read configuration from the database and compare a version integer, which is how a provider switch reaches the worker without a restart or a message bus.
  • A1Identity agent — recognises PAN / Aadhaar from OCR text (worker)
  • A2Query planner — rewrites the question, proposes filters (API)
  • A3Response composer — writes the grounded answer (API)
Every agent has a non-agent fallback. Planner fails → search the raw question. Composer fails → templated answer over the same passages. Identity fails → the document still indexes. A failed agent degrades the result; it never fails the request.
